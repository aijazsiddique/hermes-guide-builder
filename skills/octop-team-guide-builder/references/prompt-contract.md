# Octop Main-Agent Step Prompt Contract

Every implementation step generated by this skill must follow this contract.

## Required prompt skeleton

```text
PROJECT: <project name>
OCTOP BUILD GUIDE: <guide id>
STEP <NN> — <single bounded outcome>

ROLE
You are the Octop main/builder agent responsible only for this step.
Do not continue to later guide steps.

CURRENT SOURCE RULE
The guide was audited against <repo/branch/commit/date>, but your running Octop
instance is authoritative. Before changing anything, inspect the exact current
state and supported interfaces relevant to this step. If the guide and runtime
disagree, stop with CAPABILITY_BLOCKED and report the mismatch. Do not invent a
command or use private internals.

PREREQUISITES
- <prior step IDs / resources>
- <required human approval if any>

GOAL
<one measurable outcome>

INSPECT FIRST
- <commands/read paths/API/UI state to inspect>
- Reuse valid existing resources; do not duplicate them.

IMPLEMENT
1. ...
2. ...

ALLOWED SCOPE
- <specific agents/resources/files/settings>

DO NOT
- Do not change unrelated Octop/global settings.
- Do not edit octop.db or fake control-plane state.
- Do not expose secrets in output.
- Do not delete/replace existing resources unless explicitly authorized here.
- Do not mark success without running the verification below.
- Do not start the next guide step.

VERIFY
1. <functional check>
2. <configuration/state check>
3. <negative/failure check where relevant>

ACCEPTANCE CRITERIA
- ...

STOP AND REPORT
Return exactly this compact packet:
STEP_STATUS: READY_FOR_NEXT_STEP | TEST_FAILED | DEPENDENCY_BLOCKED | CAPABILITY_BLOCKED | MANUAL_CONTROL_PLANE_REQUIRED
STEP: <NN — title>
CHANGES:
- ...
CREATED_OR_UPDATED_IDS:
- ...
VERIFICATION:
- check: PASS|FAIL — evidence
BLOCKERS:
- none | ...
MANUAL_ACTION_REQUIRED:
- none | exact minimal action
NOTES_FOR_NEXT_STEP:
- ...
```

## Prompt design rules

1. One prompt = one bounded implementation outcome.
2. A step may inspect broadly but may change only its allowed scope.
3. Never tell the builder to create five agents at once. Create/configure/test in separable units.
4. Reuse existing valid resources before creating new ones.
5. Model/provider/connector names are never assumed; inspect installed/current choices.
6. If the current release lacks a supported control-plane interface from the builder context, use `MANUAL_CONTROL_PLANE_REQUIRED`; do not fall back to SQLite edits or private Python imports.
7. Prefer public CLI where the operation is supported. For operations without CLI, use a currently supported authenticated API or Dashboard/UI route if the builder genuinely has access. Verify the result afterward.
8. Native Team Host prompts must not attach unsupported Skills/MCP/plugins/execution duties.
9. Member prompts must make tool, Skill, MCP, KB, and memory responsibilities explicit.
10. Any irreversible/destructive step requires explicit human approval in prerequisites.
11. Tests must be observable; “looks correct” is not a test.
12. A failure test is required for critical routing, permissions, integrations, and autonomous actions.
13. If a member must be running for dispatch, verify it before end-to-end team testing.
14. Preserve IDs in the completion packet; downstream steps refer to actual IDs, not guessed names.
15. If current version differs materially from the audited sources, stop and regenerate the guide instead of patching around unknown behavior.

## Recommended status meanings

- `READY_FOR_NEXT_STEP`: every acceptance criterion passed.
- `TEST_FAILED`: implementation occurred, but at least one required test failed.
- `DEPENDENCY_BLOCKED`: a prerequisite resource or prior step is missing/incomplete.
- `CAPABILITY_BLOCKED`: the current Octop version does not expose/behave as the guide requires.
- `MANUAL_CONTROL_PLANE_REQUIRED`: the action is supported by Octop but not safely executable from the current main-agent context; return the smallest human UI/API/terminal action needed.
